# `detain/myadmin-plugin-installer` — full audit + Composer hook surface

**Date:** 2026-07-27 · **Package HEAD:** `76d5546` · **Composer:** 2.10.1 (plugin API `2.9.0`) · **Consumer:** `/home/sites/mystage`

---

## 1. The headline: this package is half-disabled and load-bearing at the same time

MyAdmin's `composer.json` sets `config.allow-plugins."detain/myadmin-plugin-installer": false`. That is easy to read as "this package is unused". It is not. The package has **three** independent load paths, and `allow-plugins` gates only one of them.

| Path | Gated by `allow-plugins`? | Status today |
|---|---|---|
| **Composer-plugin half** — `Plugin::activate()`, `Installer`, `CommandProvider`, `Command\*` | **Yes** — fully disabled | Dead. `activate()` never runs; no `composer myadmin:*` commands exist (verified: `composer list \| grep -i myadmin` → empty) |
| **Runtime `files` autoload** — `src/modules.php`, `src/function_requirements.php` | **No** | **Live on every request.** Sole definition site of 9 global functions |
| **Composer `scripts` callable** — `Plugin::setPermissions` | **No** | **Runs on every `composer install`/`update`**, including in CI |

### 1a. The runtime half is critical infrastructure

`src/modules.php` and `src/function_requirements.php` are `autoload.files` entries (`vendor/composer/autoload_files.php:15-16`). Composer's `files` autoloads execute during `require 'vendor/autoload.php'`, before any application code, entirely independent of the plugin allowlist.

These two files are the **only** production definition of:

`get_module_db()` · `get_module_settings()` · `register_module()` · `get_module_name()` · `get_valid_module()` · `has_module_db()` · `get_module_stuff()` · `get_service_define()` · `function_requirements()`

MyAdmin core (`include/`, `scripts/`, `public_html/`) defines **none** of them. The only same-named functions anywhere are `function_exists()`-guarded test stubs in `tests/phpunit/bootstrap.php` and `tests/phpunit/unit/Api/api_test_bootstrap.php`, which no-op in production.

`MyAdmin\Plugins\Loader` is likewise loaded by plain PSR-4 (`autoload_psr4.php:127`), instantiated at `include/tf.php:386`, and drives all **1,316** route registrations in `include/config/router.php`.

> **Removing or "cleaning up" this package fatals the entire application.** Any static-analysis or dead-code sweep that reads `allow-plugins: false` as "unused" will get this catastrophically wrong.

### 1b. Your recollection about permissions — half right

You remembered disabling the plugin to stop it writing directories. Confirmed: it **is** disabled. But **disabling it did not stop the directory writing**, and that code still runs today.

`Plugin::setPermissions()` is wired as a **Composer script**, not a plugin hook:

```
post-install-cmd / post-update-cmd → @postSetup → @setPermissions → "MyAdmin\Plugins\Plugin::setPermissions"
```

`allow-plugins` is enforced only in `PluginManager::registerPackage()`. `EventDispatcher.php` contains **zero** references to `allow-plugins`/`isPluginAllowed` (vs 24 in `PluginManager.php`). Script callables resolve through the **project** autoloader with no gating.

Physical proof — every path in `extra.writable-dirs`/`writable-files` is `0777`, every sibling is not:

```
drwxrwxrwx  include/templates          drwxrwxr-x  include/config
drwxrwxrwx  logs                       drwxr-x---  logs/mcp_cache      ← not in the list
drwxrwxrwx  logs/smarty_cache          drwxrwxr-x  public_html
-rwxrwxrwx  include/config/hooks.json      ← +x on a JSON data file
-rwxrwxrwx  include/config/plugins.json    ← +x on a JSON data file
```

What disabling **actually** did: killed `activate()` (no custom installer) and the `CommandProvider` capability (no `myadmin:*` commands). Which was accidentally protective — see §3, B2.

**Likely origin:** mystage commit `8239a6dfc5` (2022-04-25, *"fixing link"*) introduced the `allow-plugins` block with this single entry set to `false`. That is the signature of Composer 2.2's interactive prompt — answering `n` makes Composer write `false` itself. Almost certainly incidental, not a deliberate fix.

Only `--no-scripts`, or editing the `scripts` block, stops the permission run.

## 3. Real bugs, with evidence

**B1 — `getInstallPath()` template branch was unreachable.** `Installer::__construct` defaults `$type = 'library'`, and both call sites (`Plugin.php:45`, `InstallerPlugin.php:34`) omit the argument. So `$this->type === 'library'` always, and `if ($this->type == 'myadmin-template')` could never fire. Meanwhile `supports()` was a hardcoded `in_array()` ignoring `$this->type` entirely. **`supports()` and `getInstallPath()` used two incompatible notions of "type."** Verified by execution against real Composer:

```
supports('myadmin-template') = true
getInstallPath()             = /home/sites/mystage/vendor/detain/some-template
```

This is the "copying files out never worked" you remembered. The package's own `.claude/skills/installer-type/SKILL.md:62-77` documents the broken branch as the pattern to copy for new types.

**B2 — Composer 1.x API used against Composer 2.x. Critical, latent.** `installCode()` called `$this->downloadManager->download($package, $path)`. In Composer 2 `download()` and `install()` are **distinct** operations — `download()` only populates the cache; the extraction step was never invoked. Additionally `install()`/`update()`/`uninstall()` returned nothing, while Composer 2.10 returns promises that `InstallationManager` awaits. Since `addInstaller()` **prepends**, re-enabling the plugin would have handed **all 73 `myadmin-plugin` packages** to this broken installer.

**B3 — `getHttpdUser()` matches nothing. Confirmed on this box.** The regex `/^.*([a]pache|[h]ttpd|[_]www|[w]ww-data|[n]ginx)$/m` anchors to end-of-line; real `ps aux` lines end with the command tail (`/usr/sbin/apache2 -k start`). Executed: **0 matches → returns `null`**. The `[a]pache` character-class trick is the shell `grep`-self-exclusion idiom, meaningless in `preg_match`. There is also no `return` after the loop.

**B4 — `chmod 777` + `chown` with undefined variables.** `chmod 777` is applied to directories *and* data files (hence `-rwxrwxrwx` on `hooks.json`). `chown $_SERVER['USER'].':'.$http_user` — `$_SERVER['USER']` is set interactively (`my`) but **unset under `env -i`** (cron/systemd/CI). With `$http_user === null` this degrades to `chown my: <path>`, which GNU chown accepts silently (exit 0) — so B3 **fails silently forever**.

**B5 — `EnsureFileExists()` never creates files. Confirmed.** The guard is `if (!is_dir(dirname($path)))`. When the parent directory already exists — the normal case — the whole body including `touch()` is skipped. Then `chmod 777 <missing file>` exits 1, `runProcess()` throws, and the exception escapes the `foreach` in `setPermissionsChmod()` to be caught only at the top of `setPermissions()`. **One missing writable-file silently aborts every remaining path in the permission run.**

**B6 — `Loader::add_public_file()` passes 6 args to a 5-param method.** Executed result: route key is the **empty string** (so every call collides) and the methods slot holds a string where the router expects an array. PHP does not error on extra args to userland functions, so this is silent.

**B7 — `add_apmin_api_page_requirement()`: typo + wrong path.** Name should be `admin`, and it routes to `/admin/ajax/` not `/admin/apiv2/`, colliding with `add_ajax_page_requirement()`.

> *Mitigation for B6/B7:* both are latent. `add_public_file`, `add_apmin_api_page_requirement`, `add_api_page_requirement`, `add_ajax_page_requirement`, `add_root_page_requirement` and `add_public_requirement` all have **0 call sites** repo-wide. Only `add_page_requirement` (672), `add_admin_page_requirement` (206) and direct `add_route_requirement` are used.

**B8 — `SetPermissions::execute()` always fatals.** Calls `Plugin::setPermissions()` with **zero args** against `setPermissions(Event $event)`. Guaranteed `ArgumentCountError`. Currently unreachable.

**B9 — `Parse.php` cannot run at all.** `phpDocumentor\Reflection\Php\ProjectFactory` → `class_exists` = **false**. Package `phpdocumentor/reflection` is **not declared in either composer.json**. (`reflection-docblock` is present transitively — different package.) Also: `LocalFile` is handed directories, `do_call()` is a function declared inside a method body ("Cannot redeclare" on second invocation), and `$childCall` is read outside its loop scope.

**B10 — `UpdatePlugins`, `CreateUser` and base `Command` are unimplemented scaffolding.** All three print Symfony console demo boilerplate ("User Creator", `<info>foo</info>`, truncation samples) and `return 0`. `UpdatePlugins` does nothing related to its "Finds and Caches Plugins" description.

**B11 — Two live defects in the runtime half.** `modules.php:64` — `array_keys($GLOBALS['modules'])` with no `isset()` guard → `TypeError` if unset (verified fatal). `modules.php:87,96` — `get_module_settings()` on an empty `$GLOBALS['modules']` emits `Undefined array key` and returns `null` instead of `false`.

### ⚠️ The finding that changed the design

A naive "rebuild from scan results" would have **deleted those 12 live modules from MyAdmin's dispatch table**. With that rule the dry run reports `present=75, scanned=63, retained=12`, `hooks: -1`, `plugins: -64` — the 64 matching the audit's independently-derived count of dead entries.

This is exactly why the scanner reports `added`/`removed` rather than writing silently.

## 5. What's worth actually wiring up

Ranked by value-per-risk **for this project**.

### 1. Regenerate + prune `hooks.json` / `plugins.json` — `post-autoload-dump`

**Today:** both files are rebuilt **only** when an admin browses to `/admin/plugins` (`include/admin/configuration/plugins.php:125`). There is no CLI path — `plugin_find_all` has zero hits in `scripts/`. `composer myadmin:update-plugins` is a stub that prints "User Creator".

**Measured damage:** `plugins.json` holds **139 keys, 64 of them dead** — pre-rename packages (`detain/vps-module`, `detain/kvm-vps`, `detain/paypal-payments`, …) with no matching `vendor/*/src/Plugin.php`. Cause: `plugins.php:29` merges into `$plugins[$plugin]` and **never prunes**. `hooks.json` is currently clean (75 keys) but the two files' last commits are two months apart.

**Why it's feasible:** `getHooks()` implementations only touch static string properties — no app bootstrap needed — and `post-autoload-dump` has the finished autoloader available. It also fires on a bare `composer dump-autoload`, giving a free manual trigger.

**Risk control:** wrap each package in try/catch, and write only after verifying the rebuilt JSON parses and is non-empty — `include/tf.php:179` does `json_decode(file_get_contents(...))` with **no null check**, so a truncated write is an instant site-wide fatal.

### 2. Vendor working-copy dirty-check — `pre-update-cmd` / `pre-install-cmd`

**Today:** remembering to run `scripts/plugins/plugins_diff.sh` by hand.

MyAdmin sets `preferred-install: {"detain/*": "source"}` and **`discard-changes: "stash"`**, across **97 git working copies** in `vendor/`. A `composer update` therefore **silently stashes uncommitted vendor work**. `vendor/detain/myadmin-vps-module` is dirty right now.

Cheap, read-only, no false positives. Highest-consequence unautomated step in the repo. Needs an env-var escape hatch for intentional updates.

### 3. Fix the permission step that already runs — no new wiring

This is bug-fixing, not new automation. Four concrete defects:

- **Don't abort the loop on first failure** (B5) — try/catch per path inside `setPermissionsChmod()`
- **Fix the `getHttpdUser()` regex** (B3) and skip `chown` cleanly when no web user is found (B4)
- **Stop creating `vendor/detain/phpsysinfo`** — `detain/phpsysinfo` is `suggest`-only, never required, so `EnsureDirExists()` creates an **empty** directory on every install. `public_html/admin/phpsysinfo` symlinks into it, so that admin page has pointed at an empty dir for years
- **Add `logs/mcp_cache`** to `extra.writable-dirs` — currently `0750`, created ad-hoc at runtime by four different PHP entry points

### 4. MCP tool-cache bust — `post-install-cmd` / `post-update-cmd`

Replaces the `rm -f logs/mcp_cache/mcp_tools_*.php` step documented in `CLAUDE.md`, `docs/agents.md:376` and `docs/agents/skills/mcp-server-build/SKILL.md`. Near-zero risk — the cache is keyed on an md5 of the spec and rebuilds on next request. Two stale files are sitting there now (2026-05-26, 2026-06-10). Caveat: a deploy is a *proxy* for the real trigger (edits to `OpenApiParser.php`), so pair it with a `myadmin:cache-clear` command for the interactive case.

### 5. Ensure the `public_html/lib` symlink exists — `post-install-cmd`

`public_html/lib → ../node_modules/` is created by `package.json`'s `postinstall` and is **gitignored**. A fresh clone + `composer install` **without** `yarn install` leaves every JS/CSS asset 404ing, breaking `include/admin/configuration/crontab.php:165-172`, `configuration.php:147` and the DC 3D pages. Only ever create, never replace, an existing path.

### 6. Staleness warnings — `post-install-cmd`, warn-only

`public_html/spec/openapi.json` is **~2.5 months stale** (yaml 2026-07-27, json 2026-05-12). Don't *run* `composer api:yaml2json` from a hook — it needs `redocly` from npm and would fail on any box without it. Warn only.

### 7. Split the package — structural, highest payoff, highest coordination cost

Extract `Loader.php`, `modules.php`, `function_requirements.php` into a **`type: library`** package (a natural sibling to the existing `detain/myadmin-contracts`), leaving `Plugin`/`Installer`/`CommandProvider` in the `composer-plugin` package. That makes `allow-plugins` an honest kill switch instead of a trap sitting next to nine load-bearing globals.

While splitting, wrap every function in `modules.php`/`function_requirements.php` in `if (!function_exists(...))`. **The guards are currently on the wrong side**: production is unguarded, tests defend themselves. Any future core definition of e.g. `get_module_settings()` becomes an unconditional `Cannot redeclare` fatal on every request.

⚠️ Crossing this requires `composer update`, not just `git pull`, on deploy — exactly the failure mode that caused the 2026-07-21 prod blip with the contracts package.

### 8. Delete the dead surface

`InstallerPlugin`, `TemplateInstaller`, `TemplateInstallerPlugin`, `composer-plugins-installer.json` (stale alternate manifest naming dead dev-deps `satooshi/php-coveralls`, `codacy/coverage`), `.travis.yml`. Fix or delete `Parse.php` (B9), `UpdatePlugins`/`CreateUser`/`Command` (B10), and `SetPermissions::execute()` (B8). **Prerequisite work if `allow-plugins` is ever flipped to `true`** — `myadmin:set-permissions` is a guaranteed fatal today.

### Not worth automating

- **Smarty compiled-template purge** — `TFSmarty` runs `setCaching(false)` and Smarty 4's `compile_check` defaults on; stale compiles self-heal on mtime
- **DB migrations** — no runner is active; `byjg/migration` and phinx are `suggest`-only
- **Cron registration** — lives in `cron_jobs`/`cron_schedules` with its own drift detector
- **Copying vendor templates/assets into the tree** — **your instinct was right.** Zero vendor web assets exist (`find vendor/*/myadmin-* -name '*.js' -o -name '*.css' -o -name '*.png'` → 0 files). The 331 vendor `.tpl` files are shell-script templates fetched in place via `__DIR__` (`myadmin-kvm-vps/src/Plugin.php:126`). `include/templates/` is 100% first-party (618 tracked files, nothing vendor-installed), and Smarty's template dirs never include a vendor path. Copying would be pure duplication.

### ⚠️ One caution on ordering

Opportunities 1, 4 and 5 all want `post-install-cmd`/`post-update-cmd`/`post-autoload-dump` — which **already fire in CI**. `.github/workflows/tests.yml:74,179` run `composer install` **without `--no-scripts`**, across four PHP-version matrix legs plus the integration job.

The existing scripts get away with it only by accident: `getLocaleData` pipes `punic-data`'s `exit(1)` through `| grep -v SKIPPED`, and grep's exit 0 masks the failure; `setPermissions` swallows its own exception. **Don't rely on that pattern** — make every new hook explicitly no-op-or-warn when its preconditions are absent.

## 6. Composer 2.10 hook surface reference

Complete extension surface, for filling in the skeletons.

### `PluginInterface` — `PLUGIN_API_VERSION = '2.9.0'`
`activate()` · `deactivate()` · `uninstall()`. No native return types on the interface; `: void` is safe to add.

### `Capable`
`getCapabilities(): string[]`. **`CommandProvider` is the only capability interface that exists.** The `Validator` example in Composer's own docblock has no implementation. Capability constructors take exactly **one array argument** (`composer`, `io`, `plugin`).

### `EventSubscriberInterface`
`public static getSubscribedEvents()`, no return type. **Higher priority runs first.** Root-package `scripts` are appended to the priority-0 bucket *after* plugin listeners.

### All 25 events

| Class | Constants |
|---|---|
| `PluginEvents` (6) | `INIT` · `COMMAND` · `PRE_FILE_DOWNLOAD` · `POST_FILE_DOWNLOAD` · `PRE_COMMAND_RUN` · `PRE_POOL_CREATE` |
| `ScriptEvents` (12) | `PRE`/`POST_INSTALL_CMD` · `PRE`/`POST_UPDATE_CMD` · `PRE`/`POST_STATUS_CMD` · `PRE`/`POST_AUTOLOAD_DUMP` · `POST_ROOT_PACKAGE_INSTALL` · `POST_CREATE_PROJECT_CMD` · `PRE`/`POST_ARCHIVE_CMD` |
| `PackageEvents` (6) | `PRE`/`POST_PACKAGE_INSTALL` · `PRE`/`POST_PACKAGE_UPDATE` · `PRE`/`POST_PACKAGE_UNINSTALL` |
| `InstallerEvents` (1) | `PRE_OPERATIONS_EXEC` |

**Gotchas worth keeping:**
- `INIT` and `PRE_POOL_CREATE` events expose **no `getComposer()`/`getIO()`** — use the instances captured in `activate()`
- `COMMAND` fires only from ~14 specific commands, **not** from `run-script`, `config`, `exec`, `audit`, `create-project`
- `PRE_FILE_DOWNLOAD`: `setTransportOptions()` honoured for `metadata` **only**; `setCustomCacheKey()` for `package` **only**
- `POST_FILE_DOWNLOAD`: does **not** fire on a cache hit; `getPackage()` is deprecated and fires `E_USER_DEPRECATED` every call — use `getContext()`
- `POST_PACKAGE_*` are **deferred** until the whole promise batch resolves
- `PRE`/`POST_AUTOLOAD_DUMP` carry `getFlags()['optimize']`
- The six `PluginEvents` are reachable **only** from a plugin, never from `composer.json` scripts
- **`PRE_DEPENDENCIES_SOLVING`/`POST_DEPENDENCIES_SOLVING` do not exist in Composer 2** — use `PRE_POOL_CREATE`

### `InstallerInterface` — the async contract

Ten methods. **`download()`, `prepare()`, `install()`, `update()`, `uninstall()`, `cleanup()` may all return a `PromiseInterface` and the override MUST return it.** Operations are **batched across packages**: every `download()`, then every `prepare()`, then the install/update/uninstall, then `cleanup()` for every package regardless of success. Risky work and user prompts belong in `prepare()`.

**Signature trap:** `InstallerInterface` declares `prepare(string $type, …)`/`cleanup(string $type, …)`; `LibraryInstaller` declares them **without** the hint. A subclass of `LibraryInstaller` must **omit** it.

**`getInstallPath()` vs `getPackageBasePath()`:** `install()`/`update()` use the former, `uninstall()` uses the latter. Override only one and packages install to a custom path but uninstall from the wrong one.

### Other pluggable interfaces
- **Custom installers** — `$composer->getInstallationManager()->addInstaller()`. **Prepends**, so it wins over Composer's catch-all `LibraryInstaller` (registered with `type=null`, `supports()` accepts everything)
- **Custom repositories** — `getRepositoryManager()->setRepositoryClass($type, $class)`. Fixed positional constructor. Don't collide with the 15 built-in types
- **Custom downloaders** — `getDownloadManager()->setDownloader($type, $downloader)`. Unlike `InstallerInterface`, `DownloaderInterface` **does** carry native non-nullable `: PromiseInterface` returns
- **`AutoloadGenerator`** — replaceable via `$composer->setAutoloadGenerator()`, but the autoload-dump script events are almost always the right hook instead

### `extra` keys Composer understands
| Key | Effect |
|---|---|
| `class` | **Required.** String *or array of strings* — every listed class is activated independently |
| `plugin-modifies-install-path` | Sort weight `-10000`; activates before all other plugins (2.2.9+) |
| `plugin-modifies-downloads` | Own operation batch — installed & activated before other packages are *downloaded* (2.2+) |
| `plugin-optional` | Non-interactive + no matching rule ⇒ silently disabled instead of `PluginBlockedException` (2.5.3+) |

There is **no** `plugin-api-version` extra key, and no `installer-paths` in core (that's `composer/installers`).

### `config.allow-plugins`
`*` is a glob; matching is case-insensitive and anchored; **first matching pattern wins** in composer.json key order. When a plugin is blocked: silently skipped at `DEBUG` verbosity, `activate()` never called, installers not registered, subscribers not registered, commands unavailable — **but the package is still downloaded, extracted and autoloaded like any library.** That last clause is the whole reason §1a is true.

### First-install ordering caveat
On a fresh `composer install` into an empty `vendor/`, a plugin shipped as a root dependency does not exist yet when the run starts. It **misses** `INIT`, `COMMAND`, `PRE_COMMAND_RUN`, `PRE_POOL_CREATE`, `PRE_OPERATIONS_EXEC` and `PRE_INSTALL_CMD` on that run, going live mid-run via `PluginInstaller::install()`. Workarounds: `plugin-modifies-downloads`, `plugin-modifies-install-path`, or installing globally.

Also: a plugin gets a **dedicated runtime ClassLoader** covering only itself, its transitive `require`s and the root package. **Declare every dependency in the plugin's own `require`** — which is exactly why B9 (`phpdocumentor/reflection`) is a real bug and not a theoretical one.
